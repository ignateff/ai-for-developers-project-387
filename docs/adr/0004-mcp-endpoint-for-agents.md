# MCP-эндпоинт календаря для агентов

Владелец хочет работать с календарём через агента, поэтому сервис отдаёт MCP по маршруту `POST /mcp` в том же Fastify-процессе и контейнере, что и HTTP API. Отдельный сервис, stdio-процесс и вторая инфраструктура отклонены: домен, база и правила записи уже здесь, а удалённый HTTPS-эндпоинт работает с любым MCP-клиентом. `createMcpHandler` монтируется в существующее приложение через `toNodeHandler` из `@modelcontextprotocol/node`; пакет `@modelcontextprotocol/fastify` нужен только для отдельного приложения и здесь не используется.

Эндпоинт открыт без авторизации. Он отдаёт только доступность и создание записи — то же, что уже делает публичный сайт; предстоящие события через MCP не читаются, поэтому контакты гостей не раскрываются. OAuth 2.1 отклонён как несоразмерный: он требует auth-сервера и регистрации клиентов, а новых данных не защищает. Последствие принятого решения: слоты можно занять скриптом, и частота вызовов не ограничена.

Инструментов два, а не полный CRUD. `get_availability` без параметра `date` возвращает доступность всех типов встреч на 14 дней UTC, с `date` — слоты дня; так агент получает `meetingTypeId` без отдельного списка типов. `create_booking` сам берёт актуальную версию типа встречи и выводит `Idempotency-Key` из типа, слота и почты гостя, поэтому повтор после сетевой ошибки не создаёт вторую запись. Удаление и «забыть попытку» агенту недоступны: необратимые операции остаются человеку.

Времена только в UTC, как в API. Инструменты и их описания — на английском, потому что это интерфейс для модели; тексты ошибок HTTP-API остаются русскими для гостя. MCP не описывается в TypeSpec и OpenAPI: протокол другой, а поведение фиксируют интеграционные тесты с официальным клиентом. Если через MCP появится чтение предстоящих событий или другие персональные данные, решение об отсутствии авторизации нужно пересмотреть.
