# PR attempt budget adapter

## Command budget v2

Commands in PRs use Actions run and attempt history, not the issue-comment counter. The command job is serialized by PR and checks history after authorization and before the named admission step and model. Three successful admission steps exhaust the budget across general and inline comments. An admitted attempt is counted even if preparation, model, cancellation, timeout or a job rerun later fails. Normal issue commands are not limited by this PR budget. A refusal reports `limit_exhausted`, the checked SHA and run link through a separate job with `pull-requests: write`; the model job retains `pull-requests: read`. Missing or incomplete history fails closed as `infra` when PR identity is available.

The cutover excludes run IDs at or below `42404073264`; old history is not migrated. GitHub can rerun historical workflows using their old workflow definition, so operators must not rerun old model-capable jobs. This code cannot disable those old definitions. New job reruns check admission again. API responses may lag; unavailable steps fail closed. Pagination and 100-job limits also fail closed. Counting depends on retained complete Actions history, unchanged workflow configuration and repository administrators. Deleting runs, partial API visibility, eventual consistency, external workflows or privileged changes can weaken the limit; it is best effort, not a monetary ceiling. The agent token has Actions read, not Actions write. A new PR has a new budget.

The model step has its own timeout so reporting can run; forced cancellation or runner loss can prevent a report. `timeout` is reported for a confirmed command timeout, `infra` for preparation or missing credentials, and `agent_failed` for other command failures. An uncertain failure needs log inspection. The separate review workflow continues using the old comment-based review counter described below.

## Legacy review budget

The adapter in `scripts/opencode-budget-workflow.ts` remains wired into the review model job. The reviewer loads changed-file contents at pinned base/head SHAs and linked context when available, while reporting incomplete evidence and the absence of a full repository snapshot. An earlier controlled full GitHub review timed out; a later review completed and published a report on [PR #62](https://github.com/ignateff/ai-for-developers-project-387/pull/62) ([run 42463395746](https://github.com/ignateff/ai-for-developers-project-387/actions/runs/42463395746)). This does not establish every review scenario or cross-runner behavior.

The trusted workflow orchestrator receives the provider key as a job-step environment variable, removes it from the process environment before admission, and excludes it from preparation; only the model/runtime invocation receives it after admission. This is not the same as withholding the secret from the trusted orchestrator itself.

The legacy adapter stores command and review counters in one PR issue comment, distinct from review reports; only the review counter is used by the current workflow. Its trusted caller supplies the expected numeric comment author ID. A matching marker without that author is ignored. After trust checks it creates the state if missing and increments the relevant count before runtime preparation; an error or cancellation after the update can therefore consume an attempt. Re-running a model-capable adapter invocation requires a fresh admission; publication-only mode does not run the model. Ordinary issues do not receive a PR budget.

The comment body is exactly the marker on one line and the JSON object on the next line, for example:

```text
<!-- opencode-pr-attempt-budget:v1 -->
{"command":0,"review":0}
```

An authorized maintainer can edit the two non-negative integer values to correct or reset the budget. Keep the exact format and author: invalid content or multiple matching comments cause `infra`, requiring a human to resolve the ambiguity. Deleting the comment loses history; the next admission creates a zero state and does not recover old attempts. Both a human and an agent with sufficient rights may edit or delete it.

Legacy review execution uses its own Actions concurrency group. Its budget update uses a separate short-lived queue: each contender creates a temporary issue comment with marker `<!-- opencode-pr-budget-lock:v1 -->`, verifies the expected numeric bot author and waits for older claims to disappear, then removes its own claim before runtime preparation. These are coordination comments, not counter or review-report comments. Creating them can generate GitHub notifications and secondary rate limiting. After forced cancellation a claim can remain: a maintainer must confirm its run has stopped before manually deleting it. Waiting contenders time out and fail closed rather than silently stealing it.

An unsuccessful or malformed response to the lock-creation POST is ambiguous: GitHub may have created the claim even if the client received no response. The log reports an unknown outcome and PR number without printing API diagnostics. A maintainer must inspect **all pages** of PR comments for the lock marker and expected numeric bot author ID, check that the corresponding run is no longer active, then remove only the orphaned lock comment. Do not delete the separate budget comment or remove a potentially active lock. If ownership or activity is uncertain, stop and investigate rather than guessing. A manually removed lock can allow a later attempt; the unknown POST did not itself increment the counters.

The queue is **best effort**: listing pages and creating/deleting comments are not an atomic transaction; concurrent comment insertions or deletions can shift offset-based pages, causing an earlier lock to be missed even when both runners are healthy. Incomplete visibility, cancellation, human edits, or a second implementation that ignores the queue can also lose updates. This is not tamper protection, a strict attempt limit, or a monetary ceiling. One model invocation may produce multiple provider requests. Admission stays inside each model-capable job: re-running that job rechecks and spends again. The distinct publication job downloads the original result artifact; re-running only publication neither checks the budget nor invokes the model. It checks current head before posting and avoids reposting an already published artifact; concurrent head changes or publications are still not atomic.

GitHub documents concurrency at [workflow/job scope](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), and notes that [re-running a specific job retains outputs of jobs not rerun](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs). A separate successful budget job alone would therefore be unsafe for a model-job rerun. The [issue comments API](https://docs.github.com/en/rest/issues/comments) provides create/list/update/delete, not an atomic compare-and-swap. Inspect real runs and their limitations before relying on the review.
