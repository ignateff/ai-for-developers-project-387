# План: цикл реализации и ревью PR

Цель — настроить и продемонстрировать цикл от реализации до release PR. Исходного тикета и согласованной спецификации пока нет: инфраструктуру можно подготовить без них; для демонстрации потребуется отдельно согласовать изменение, сценарии и зафиксировать решение человека.

## 1. Проверить существующую инфраструктуру

- [ ] Сверить текущие workflow, скрипты и документацию с требованиями; выделить уже работающие части и пробелы.
- [ ] Проверить настройки GitHub App, секрет модели, доверенных авторов и ветки; недоверенным fork не предоставлять секрет.
- [ ] Проверить защиту main и обязательный CI; если она недоступна, записать ограничение и порядок ручной проверки.
- [ ] Выбрать и зафиксировать демонстрационное изменение и его основной, негативный и соседний сценарии; получить согласование человека. Не выдумывать ссылки на тикеты.

## 2. Подготовить авторевью и PR

- [ ] До PR реализации проверить и включить независимый workflow на `pull_request`: отдельный CLI OpenCode, права, тайм-аут, отмена устаревших запусков, проверка доверия и запрет правок кода.
- [ ] Добавить `REVIEW.md` с критериями календаря и явно передавать его ревьюеру вместе с контекстом согласования, diff и доступными результатами CI.
- [ ] Требовать от замечаний файл, строку, условия и последствия; при отсутствии подтверждённых дефектов сообщать об этом. Учитывать ранее разобранные замечания.
- [ ] Создать шаблон PR с разделами проверок, риска и отката; предусмотреть команды, ссылки на прогоны, SHA и рассмотрение данных при откате.
- [ ] Обновить README: запуск, права, ограничения, настройки и порядок проверки авторевью.

## 3. Проверить бюджет команд

- [ ] До вызова модели ограничить число допущенных команд человека на PR, учитывая оба канала комментариев, отмены, тайм-ауты и Re-run.
- [ ] Убедиться, что состояние сохраняется между запусками и токен агента не может его переписать; описать ограничения истории Actions и прав администратора.
- [ ] Отдельным шагом без модели публиковать `limit_exhausted`, `timeout`, `infra` или `agent_failed`, SHA и ссылку на логи; оставить время для публикации после остановки агента.
- [ ] Проверить механизм тестами и учебным запросом после исчерпания бюджета; сохранить ссылку на запуск и подтвердить отсутствие вызова модели.

## 4. Реализовать демонстрационное изменение

- [ ] Проверить сохранённые правила `AGENTS.md` и `docs/agents/`, включая Conventional Commits; учесть требование проекта о ссылке на issue в коммитах, если issue появится.
- [ ] Выполнить согласованное изменение в общей ветке с помощью `implement-spec`, насколько его процесс применим без тикетов; зафиксировать ограничения отсутствующего issue.
- [ ] Добавить тесты основного и негативного сценариев. Показать отказ при отсутствующем или сломанном поведении и успешный прогон после исправления.
- [ ] Провести общее ревью собранной ветки и подготовить PR: согласование, объём, проверки с SHA и ссылками, риск и откат. Ссылки и `Closes` указывать только для реально существующих issue.

## 5. Провести независимую проверку PR

- [ ] Проверить автоматический CI и отдельное авторевью; отсутствие доступной спецификации или согласования должно быть явно отмечено.
- [ ] Оставить общий комментарий и комментарий к строке diff с `/oc`; убедиться, что агент получает контекст и вносит правки в ту же ветку.
- [ ] Разобрать каждое замечание: подтвердить и передать исправление человеку или отклонить с объяснением. Повторно проверить изменённое поведение, CI и ревью.
- [ ] Превратить одну обнаруженную проблему в регрессионный тест, правило линтера или уточнение инструкций и подтвердить, что защита обнаруживает тот же класс ошибки.

## 6. Проверить head и завершить цикл

- [ ] В отдельном CI-задании выполнить checkout точного `github.event.pull_request.head.sha`, записать `git rev-parse HEAD` и запустить независимую браузерную проверку основного и соседнего сценариев.
- [ ] Сохранить результат, SHA и Playwright trace или скриншот в артефакте; включить trace и для успешного прогона. После каждого нового push повторять проверку.
- [ ] Перед мержем открыть артефакт, сверить SHA с текущим head, проверить статусы и замечания; человеку зафиксировать решение о мерже.
- [ ] Проверить итоговое сообщение коммита на Conventional Commits и после мержа найти созданный или обновлённый release-PR. При необходимости проверить настройки Actions и ручное подтверждение запусков.

## Результаты первичной проверки инфраструктуры

Проверено на базе `4eecc31`; настройки GitHub прочитаны 7 ноября 2026 года. Это аудит конфигурации, а не подтверждение успешного реального запуска агента.

- CI запускается на PR и выполняет `mise run check`, включая тесты, линтер и Playwright. Checkout использует стандартный ref события PR; отдельного артефакта с точным head SHA и trace успешного прогона в CI не настроено.
- `opencode-review` подписан на PR, имеет тайм-аут и отменяет устаревшие задания, но отключён и в YAML (`if: false`), и в настройках Actions. Документация сообщает, что полный контекст согласования, CI и предыдущих ревью ещё не собирается. Включать до устранения пробелов рано.
- Команды `/oc` обрабатываются отдельно для общих и построчных комментариев; в коде и тестах предусмотрены проверки доверия и отказ для fork. Наличие ключа модели, фактические права App и реальное поведение на GitHub ещё не проверены.
- Бюджет существует до вызова модели, но хранится в редактируемом комментарии и использует best-effort блокировку. По документации он не защищён от сброса и гонок, поэтому требованию о независимом счётчике не соответствует.
- Шаблон PR существует; его содержание ещё нужно сопоставить с критериями. `REVIEW.md` отсутствует.
- На GitHub защита ветки main отсутствует, применённых правил rulesets нет. До настройки обязательного CI человек должен проверять актуальный SHA и все статусы вручную перед мержем. Доступность настройки на тарифе не установлена.
- Release Please включён и использует GitHub App; факт действительности App и создание release PR в демонстрационном цикле ещё предстоит проверить. У стандартного workflow token разрешения по умолчанию — read.
- Локальная базовая проверка: 456 тестов и 39 E2E прошли; `mise run check` остановился на Docker smoke из-за неотслеживаемого файла плана, не включённого в разрешённый список контекста.
- Демонстрационное изменение, критерии и согласование человека пока не выбраны. До их появления соответствующую часть этапа и демонстрацию завершить нельзя.

## Предварительная проверка бюджета

- API последних запусков `opencode.yml` для `issue_comment` возвращает пустой `pull_requests`; `head_sha` относится к ref запуска и сам по себе не связывает команду с PR. Один лишь список runs с `run_attempt` не позволяет корректно восстановить бюджет текущих запусков.
- Текущий job сериализован по номеру issue/PR через `queue: max`, но счётчик и блокировка — редактируемые issue-комментарии. Агенту доступны `issues: write`; отдельного `actions: read` в command job нет.
- Re-run отдельного job может использовать выводы jobs предыдущей попытки. Допуск обязан выполняться внутри каждого model-capable job; считать сам `run_attempt` без проверки фактического допуска недостаточно.
- Потребуется проверяемая запись допуска, связанная с PR, run ID и номером попытки, в хранилище, недоступном токену агента на запись; либо доказуемая конструкция на данных Actions. Нужна миграция с явной границей учёта и fail-closed при неполной истории. Очередь ограничена 100 ожидающими заданиями; её нельзя считать долговечным журналом.
- Публикация результата сейчас не гарантирована при принудительной отмене; `limit_exhausted` в CLI выводится в лог, а отдельный отчёт для команд требуется доработать.
- До реализации проверить фактические разрешения токена приложения и доступность выбранного защищённого хранилища; не утверждать, что одна история Actions удовлетворяет требованиям.

### Уточнение перед реализацией бюджета

- По решению человека старые запуски не учитываются. Граница должна быть задана явно в версии workflow; обработку старых Re-run нужно закрыть, иначе они смогут обойти новый механизм.
- История jobs конкретной попытки доступна через API и содержит статусы шагов. Возможный вариант для проверки: имя job содержит номер PR, успешный шаг допуска предшествует модели, а последующие запуски под той же очередью читают шаги всех попыток. До выбора решения необходимо подтвердить своевременную видимость шагов, обработку отмены между допуском и моделью, отдельного Re-run и неполной/удалённой истории; без доказательств — fail closed.
- Хранение логов и артефактов Actions настроено на 90 дней; нельзя молча трактовать исчезнувшую историю как нулевой бюджет. Администратор может удалить историю; ограничение действует при её сохранности.
- Установлены секрет модели и данные Release Please App (проверены только имена); отдельный App для бюджета по именам переменных не обнаружен. Доступ к списку установок и фактическим разрешениям App текущий пользовательский токен не предоставил (HTTP 403/401), поэтому их подтверждение остаётся открытым.
- Токен команд передаётся в окружение агента и имеет issues: write; новые записи бюджета нельзя доверять комментариям этого токена. Конфигурация Actions включена, разрешения workflow по умолчанию read.

### Проверка готовности авторевью

Проверено 7 ноября 2026 года по локальному коду и настройкам GitHub. Сборщик загружает связанные доступные issue, явно связанные комментарии согласования, diff и снимки изменённых файлов, проверки head SHA и предыдущие отзывы; недоступные источники и неполные данные отмечаются. При повторном ревью предыдущие построчные замечания дополнены координатами, commit и diff hunk. Источники вне поддерживаемых репозиториев и неоднозначные ссылки не считаются проверенными; полный репозиторий не собирается.

Проверка доверия допускает владельца, авторизованных участников и только явно разрешённые идентификаторы известных ботов; отклоняет PR из fork и ошибки проверки. В GitHub переменная OPENCODE_REVIEW_APP_IDS не задана, поэтому PR приложения пока не допускается. Workflow отключён в Actions и в YAML; REVIEW.md пока есть только в рабочей ветке, а загрузка идёт из base. Требуется проверить реальные права токена и публикацию на доверенном PR после интеграции кода и настройки доверенного ID.

Локально 94 целевых теста прошли. Проверка закреплённого CLI с локальным провайдером `mise run test:opencode-review-runtime` не дошла до сценариев: загрузка архива завершилась ошибкой сети, HTTP, размера или тайм-аутом; успешность runtime не подтверждена. Реальные вызовы модели и публикация в GitHub в ходе этого аудита не выполнялись. Перед включением необходима успешная проверка runtime и контролируемая проверка GitHub.

Это испытание инфраструктуры на существующих сценариях, а не свидетельство согласованной демонстрационной доработки.

### Согласованная демонстрационная доработка

Человек согласовал в этом чате кнопку «Скопировать детали» на экране успешной записи без создания тикета. Основной сценарий: скопировать тип встречи, отображаемую дату, диапазон времени и UTC, показать подтверждение. Негативный: если буфер недоступен или отклонил запись, показать понятную ошибку и оставить детали видимыми. Соседний: кнопка повторной записи продолжает работать после попытки копирования. Персональные данные в копируемый текст не включать. Это согласование в чате, а не ссылка на GitHub Issues: исходное требование о спецификации и ссылке на согласование в GitHub этим не выполнено.

### Реализация копирования деталей

В текущей ветке добавлены кнопка копирования, подтверждение и сообщение при отказе буфера; используются те же отображаемые тип, дата, время и UTC без персональных данных. Проверки добавлены на согласованных границах: компонент и браузер. Первый компонентный тест не проходил на версии без кнопки и прошёл после реализации; соседние сценарии существующей записи проходили до изменения. Сценарии копирования и отказа включены в head-browser; полный GitHub-прогон для итогового head ещё нужен.

### Расширение контекста независимого авторевью (#74)

Сборщик контекста получает деревья base/head через Git Trees API и включает в снимок выбранные неизменённые связанные файлы: зависимости изменённого кода, импортёров, найденных ограниченным read-only поиском ссылок, тесты рядом с изменениями, файлы того же каталога и цепочку контракта/OpenAPI/SDK для изменений API. Неизменённость подтверждается совпадением blob SHA в base и head, поэтому одна версия содержимого действительна на обоих зафиксированных коммитах. Добавлены индекс путей (до 5000 записей), список коммитов PR для связи прежних замечаний с исправлениями и явные ограничения при недоступности, усечении или сокращении контекста.

Адаптер `scripts/opencode-review.ts` дополнительно материализует связанные файлы в `repository/<path>` изолированного workspace: read-only инструменты ревьюера могут искать и читать их, не исполняя код PR. Проверка «прочитаны все фрагменты снимка», доверие автору/ветке, защита секретов, тайм-аут и отмена устаревшего ревью сохранены.

Локально проверены: сбор связанных неизменённых файлов на примере изменения, для оценки которого нужны неизменённые модуль из другого каталога, его импортёр и тест; исключение файла, различающегося между base и head, с явным ограничением; явное сообщение при недоступном или повреждённом дереве; усечение индекса и ограничения размера; проверка истории коммитов и отказ при небезопасных путях; обновлённый текст публикации с предупреждением о неполном контексте. Тесты используют подменённые GitHub API и runtime. Реальный прогон GitHub с расширенным контекстом после этого изменения не выполнялся и требует отдельного разрешения; зелёный локальный прогон не доказывает права токена, поведение модели или публикацию.
